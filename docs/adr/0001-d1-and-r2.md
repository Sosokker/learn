# 0001. D1 for metadata, R2 for lesson bodies (no Postgres)

- Status: accepted
- Date: 2026-10-07

## Context

The template uses Postgres through Hyperdrive. The user decided: no Postgres,
Cloudflare only. Lessons are big JSON documents (30–150 KB, up to 512 KB).
Metadata (users, lessons, tags, counters, search) is small and relational. D1
bills rows read and written, and a database holds at most 10 GB.

## Decision

- **D1** (SQLite) holds metadata, counters and the concept search index.
  Tables are Drizzle `sqlite-core` (`packages/db/src/schema.ts`).
- Drizzle only builds SQL (`.toSQL()`, `sqlite-proxy` driver). `@effect/sql-d1`
  runs it, and rows are decoded with Effect Schema (`Database` in
  `packages/db/src/database.ts`). This is the template's pattern on another
  driver.
- **R2** holds lesson and concept bodies, one immutable file per version (see
  ADR 0003). D1 rows keep only the hash and size.
- No orgs and no row-level security. Owner and visibility rules live in
  `packages/services`.

## Why

- Near-zero fixed cost: D1 and R2 fit inside Workers Paid ($5/month) for the
  expected load. No database server, no connection pool.
- Keeping bodies out of D1 keeps the database small and row reads cheap. R2
  egress is free.
- The Storage seam (`packages/services/src/storage.ts`) and the Drizzle
  builder keep the door open to another SQL or object store.

## Cost

- D1 bills rows *scanned*, so a missing index is a cost bug. Every list needs a
  covering index, keyset paging, and no `OFFSET` or `COUNT(*)`.
- No interactive transactions. Multi-row changes must be one `db.batch()`, and
  reads before the batch can race (unique constraints catch the important
  cases, such as `unique(lesson_id, lang, n)`).
- SQLite only: no RLS, no `ILIKE` indexes, FTS5 instead of Postgres search.
  FTS5 tables can't be declared in Drizzle and block `wrangler d1 export`
  (see `packages/db/README.md`).
- drizzle-kit writes folder migrations, which wrangler can't read, so a
  flatten script sits between them.
